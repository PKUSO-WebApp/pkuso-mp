# 登录失败判读手册（diag 对账）

写给**之后的智能体/人**：拿到「用户登录失败」的报告时，怎么用 `x-pkuso-diag` 这条关联 id
把客户端与服务端的记录对起来，判断**断在哪一步**、**请求到底有没有送到**。

相关代码：客户端 `pkuso-mp/src/lib/diag.ts` + `src/lib/supabase.ts`(taroFetch) + `src/lib/error-report.ts`；
服务端 `pkuso-backend/supabase/functions/_shared/diag.ts` + `wechat-auth` / `send-login-code` / `login-with-code`。

---

## 0. 一句话

**旧埋点**：两端各有一堆记录，但没有任何字段能证明它们说的是同一次请求（登录失败时客户端还没有
会话，cel 行的 `user_id` 是 `null`，只有时间戳可猜）。
**现在**：客户端每个请求带 `x-pkuso-diag`，服务端把它写进每一条函数日志，失败时客户端把**同一个值**
写进 `client_error_logs`。于是「请求有没有送到服务端」从**推测**变成**对账**。

---

## 1. id 的形状与解析

```
x61lq3lw-8-muk5wzr0-g9km
└──┬───┘ │ └───┬──┘ └┬─┘
 install 序号  时间36  随机4
```

| 段 | 含义 | 用途 |
|---|---|---|
| install（8 字符 `[0-9a-z]`） | 安装级，持久化在 storage | 同一台设备的多次失败**聚合**；清缓存/重装会变 |
| seq（36 进制，进程内自增） | 本次运行内第几个请求 | 同一次运行内的**先后顺序**（重启后从 1 重来） |
| t（36 进制毫秒） + rand（4 字符） | 跨进程/跨重启兜底 | 保证不同请求不撞 id（撞了会把两次请求错认成同一次） |

- 三段都由 `-` 分隔，各段内**不含** `-`，所以按 `-` split 即可解析。
- 服务端契约：`[A-Za-z0-9._-]{1,64}`。**不合契约的头一律当「没带」**（记 `diag: null`），且
  **静默丢弃**、不报错。所以客户端拼 id 时绝不能塞中文/空格。
- 服务端对**没有**带头的请求记 `"diag": null`（字段仍在）——老版本客户端就是这种。

## 2. 两边的记录怎么取

### 客户端：`client_error_logs`

```sql
-- 按 diag 找（detail 是 jsonb）
select id, created_at, received_at, event, level, message, detail, app_version, platform, page
from client_error_logs
where detail->>'diag' = '<完整 diag>';
-- 按设备找（install 前缀锁同一台设备）
select * from client_error_logs where detail->>'diag' like 'x61lq3lw-%' order by id;
```

- **只有失败会上报**（error/warn），成功不写。所以「表里没有」= 那次没报错。
- `created_at` 是**客户端本机钟**（错误发生时刻），`received_at` 是**服务端收到时刻**。
  两者之差 = 断网积压窗口（实测 12–16s）。**跨端对账别用绝对时间，用 diag。**
- 典型 detail 形态（按 `event` 分）：

| event | detail 键 |
|---|---|
| `request_failed` | `urlPath` `method` `diag` `ms` + `errRaw`（网络层失败）或 `status`（HTTP 失败） |
| `wechat_login`（step=invoke） | `step` `diag` `errorName` `httpStatus` `serverError` |
| `wechat_login`（step=set_session） | `step` `diag` `errorName` `errorCode` `httpStatus` |
| `wechat_login`（step=wx_login） | `step` `errMsg` — **没有 diag**（还没发出任何请求） |
| 任意 | `netLastKnown`（见 §5，别当实时网络状态用） |

### 服务端：`function_logs`（Supabase 日志流）

```sql
select timestamp, event_message from logs
where source = 'function_logs' and event_message like '%<完整 diag>%'
order by timestamp;
```

- ⚠️ **正文在顶层列 `event_message`**，**不是** `log_attributes['event_message']`（后者查回空；
  那里只有 `event_type`/`execution_id`/`request_id`/`deployment_id`/`version` 等元数据）。
- ⚠️ `function_logs` / `function_edge_logs` **只在真有调用时才有行**；没有调用时整个 source
  在 `group by source` 里都不出现。**别把「查不到」读成「日志坏了」**。
- `log_attributes['version']` 是每次部署递增的版本号，可用来判断某条日志属于哪一次部署。
- 服务端每条日志含：`fn` `diag` `event` `ms`（**相对本次请求起点的累计耗时**）+ 该步的字段。
  `wechat-auth` 的典型步：`code2session` → `rotate_password` → `ok`，失败则 `fail` + `step`/`status`/`error`。

## 3. 判读表（核心）

对 `wechat-auth` / `send-login-code` / `login-with-code` 这三个**边缘函数**端点：

| 客户端看到 | 服务端（同一个 diag） | 结论 |
|---|---|---|
| `wechat_login` / `step=wx_login`（无 diag） | 无 | 断在 `wx.login`：**请求根本没发出去**，代码在 wx.login 失败后就 return 了 |
| `request_failed @ /functions/v1/…`，`errorName=FunctionsFetchError` | **该 diag 零行** | 请求**没送到**服务端（发出即失败 / 被挡在边缘之前） |
| 同上，但 `errRaw` 里带 `ERR_*`、`ms` 很短 | 零行 | 同上，且是链路层立刻失败（DNS/连接拒绝） |
| 同上，`ms` 很长（秒级～几十秒） | **有该 diag 的行** | 请求**送到了**，断在返回路上 —— 用服务端的 `step` 看它走到了哪一步 |
| 客户端记失败 | **`event: ok`** | **服务端成功了，响应没回来**：密码已轮换、会话已签发，而用户以为没登上。**旧埋点完全看不见这一类** |
| 客户端记失败 | `fail` + `step`/`status`/`error` | 服务端确实失败，`error` 字符串（如 `token exchange failed`）就是根因 |
| `httpStatus: 502/504/546` | 该 diag 零行或只有平台行 | **平台网关/运行时**问题（响应体不是我们的 JSON，所以 `serverError` 是空串）；HTTP 状态码是唯一分界 |

### ⚠️ 关键边界：只有 `/functions/v1/*` 能用 diag 对账

`apikey` 之外的自定义头，**PostgREST（`/rest/v1/*`）与 GoTrue（`/auth/v1/*`）不会记进日志**。
所以那两类的 cel 行（例如 `request:fail @ /rest/v1/rpc/check_data_versions`）**在服务端永远查不到该 diag** ——
这**不代表请求没送到**，只代表"那条路径上没有人会记它"。判断它们只能退回**路径 + 时间戳**
（`postgrest_logs` / `auth_logs` 里有请求路径与状态码），属于弱证据。

## 4. 「同一性」能判到什么程度

| 问题 | 能否硬判 | 凭据 | 边界 |
|---|---|---|---|
| **同一次请求** | ✅ 能 | `diag` 逐字节相同 | 前提是请求打的是边缘函数（见 §3 边界） |
| **同一台设备/安装** | ✅ 能 | install 前缀相同 | ≠ 同一个人（换人用同一台设备也相同）；清缓存会换前缀 |
| **同一个人** | ⚠️ 部分 | 服务端 `code2session` 行的 `openid8`（微信账号前 8 位，隐私截断） | 只在走到 code2session **之后**才有；断在更早的失败（如 wx.login）没有任何身份标识。客户端 `user_id` 在登录失败时**必然是 null**（会话还没建立）。`openid8` 是截断值，别当主键 |
| **同一次「登录尝试」** | ❌ **不能** | — | `diag` 是**每请求**一个：一次登录尝试里的 `check_data_versions`、`wechat-auth`、`setSession` 各自一个 id，只能靠 install 前缀 + 时间邻近**推测**归组。要硬判需加 attempt id（见 §7） |

## 5. 别过度解读这几件事

1. **`netLastKnown` 不是"失败那一刻的网络状态"**。它是缓存值（`getNetworkType` 只有异步版，报错路径要同步可得），
   刷新点在启动、网络变化回调、每次上报之后。**实测**：开发者工具模拟离线时它仍显示 `wifi`——
   因为工具模拟的是"请求失败"而非系统网络变化，`onNetworkStatusChange` 不响。
2. **行数 ≠ 发生次数**。同一指纹（`event` + `message` 前 120 字）在 **5 分钟**内只报一次（防循环写爆库）。
   求"发生了几次"要看服务端日志或放宽去重。
3. **时间戳有钟差**。客户端 `created_at` 是本机钟，服务端 `timestamp` 是服务端钟；两者可能差几百毫秒到几秒。
   看似"服务端早于客户端"通常只是钟差。**对账用 diag，不用时间。**
4. **请求"发出后、到达边缘前"断掉**这一段，与"压根没发出"**分不干净**：两边都表现为
   "客户端有失败、服务端零行"，只有 `ms` 与 `errRaw` 的差别，而它们是辅助证据不是判据。
   别把这种情况说成"能确定是链路丢包"。
5. **清缓存会换 install 前缀**。同一个开发者工具里两次操作前缀不同，说明中间清过缓存/重开过项目——
   这不矛盾，也顺带说明**进程内的去重表跟着被清空**（所以两次相同的失败可能都留下了）。
6. 客户端 `ms` 只对**失败**的请求有值（成功不写库）。服务端 `ms` 是**累计**耗时（不是分步）。

## 6. 黄金样例（2026-09-27 prod 实测，可直接拿去对照格式）

同一位开发者、同一个工具，三次操作：

### ① 登录成功
```
服务端 18:37:10.728  {step:code2session,  ms:527,  diag:"9bvxfva5-9-muk5un89-5c8w", openid8:"o12bmxYz"}
服务端 18:37:12.068  {step:rotate_password, ms:1867, diag:"9bvxfva5-9-muk5un89-5c8w"}
服务端 18:37:12.359  {event:ok, ms:2158, diag:"9bvxfva5-9-muk5un89-5c8w"}
客户端：零行（成功不上报）
```

### ② 先断网，再点登录
```
客户端 18:38:24.188  request_failed @ /rest/v1/rpc/check_data_versions  ms:8023  diag:"rb0g8bak-8-…"
客户端 18:38:24.200  wechat_login / step:wx_login  "login:fail \"undefined\" is not valid JSON"   ← 无 diag
服务端：整个窗口零行
```
结论：断在 `wx.login`，**连 invoke 都没走到**（没有 `/functions/v1/wechat-auth` 的请求行）。
两条客户端记录在 18:38:40 补送成功（`received_at` − `created_at` = 16s，断网窗口）。

### ③ 点击登录后、请求期间断网（**本次改动最有价值的形态**）
```
服务端 18:38:59.784  {step:code2session,  ms:681,  diag:"x61lq3lw-8-muk5wzr0-g9km"}
服务端 18:39:00.698  {step:rotate_password, ms:1596, diag:"x61lq3lw-8-muk5wzr0-g9km"}
服务端 18:39:01.029  {event:ok, ms:1927, diag:"x61lq3lw-8-muk5wzr0-g9km"}      ← 服务端完整成功
客户端 18:39:36.505  request_failed @ /rest/v1/rpc/check_data_versions  ms:5701  diag:"x61lq3lw-9-…"
客户端 18:39:41.812  request_failed @ /functions/v1/wechat-auth  ms:40694
                     errRaw:{"errMsg":"request:fail"}  diag:"x61lq3lw-8-muk5wzr0-g9km"   ← 同一个 id
客户端 18:39:41.814  wechat_login / step:invoke  FunctionsFetchError  diag:"x61lq3lw-8-muk5wzr0-g9km"
```
结论：**服务端已把这次登录跑完并 `ok`（密码已轮换、会话已签发），客户端等了 40.7 秒才失败** ——
响应没回来。用户看到的是「微信登录失败，请重试」，而库里那行是成功。
`x61lq3lw-8`（wechat-auth）与 `x61lq3lw-9`（check_data_versions）共享 install 前缀、序号连着，
说明是同一台设备上紧邻的两次请求。

## 7. 想把「同一次登录尝试」也变成硬凭据（**未做**，方案）

现状：一次用户动作里的多个请求各自一个 diag，归组只能推测。要硬判，二选一：

- **改 id 形状**：`<install>-<attemptSeq>-<reqSeq>-<t>-<rand>`，同一次动作里的请求共享 `attemptSeq`。
  服务端契约不变（仍是 `[A-Za-z0-9._-]{1,64}`），但两端的解析/生成都要改，且**老记录没有中间段**，
  判读时要兼容两种形状。
- **加一个头** `x-pkuso-attempt`：语义更清楚，但要在 `_shared/diag.ts` 里加读取+校验、加进
  `CORS_ALLOW_HEADERS`、并让三个函数都记这个字段。

代价都不大，但都需要**两端一起改**（含 prod 部署）。做之前先想清楚：现在"推测归组"是否真的
不够用——大多数排查只需要「这一次请求送到了吗」，那一条 diag 就够。
